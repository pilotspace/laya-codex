# Plan 2026-10: fewer lookup round trips with a whole-chunk Laya

Status: done 2026-10-09; it ships as v0.5.0 ([release plan](2026-10-release-v0.5.0.md)). Proposed
2026-10-07 after an owner interview the same day; evidence from benchmark v14 (held-out) and a
warm-daemon stage profile (2026-10-06/07).

**Result (benchmark v15, held-out, v0.5.0 vs stock).**

| | v14 (v0.4.0's ranking) | v15 (v0.5.0) |
|---|---|---|
| Lookup calls per session | 1.82 | 1.83 |
| Lookup time | 5.60 s | 5.36 s |
| Speed-up over stock lookups | 1.6× | **2.0×** (10.55 s) |
| Hook per prompt | 0.53 s | 0.15 s (0.13 s idle) |
| First-question recall | +0.099 | +0.111 |
| Cost | −3.4% | −6.6% |

- The hook target (≤ 0.5 s) and the quality goal were met.
- Lookup calls did not fall: the gain is the faster hook and `search`, not fewer round trips.
- Against v0.4.0 in the same run: lookup calls −9.8% (n.s.), lookup time −16.7%.
- WS5, follow-up picks, is parked. The window bet did not pay: r2 ranks best at 128 tokens.

## Outcome

Claude goes from the prompt to the answer with fewer Grep / Read / `search` round trips, because
Laya puts the right code (and, on the follow-up, the right callers and tests) in front of it first.

| decision (owner, 2026-10-07) | |
|---|---|
| What "2× faster lookup" means | fewer lookup round trips (each ≈ 2.3 s; 76% of lookup time) |
| Audience | open-source users on Apple Silicon (Metal) |
| Quality | must improve, not just hold |
| Hook latency | p50 ≤ 0.5 s per prompt (today 0.53 s) |
| Cost | the −15% cost target binds: no change may make sessions dearer |
| Model | a smaller model retrained at whole-chunk windows (512 tokens), trained locally; a wider candidate pool |
| Follow-up | in scope: the model reads the follow-up and Claude's first answer to pick the callers/tests to inject |
| Order | measurement fixes first |
| Tracking | this plan; one branch and PR per workstream |

Levers (docs/VISION.md): **Precision** (WS2–WS4), **Pull** (WS5: answer the follow-up's lookup
before Claude makes it), **Honest measurement** (WS1, WS6).

## Baseline (v14 held-out, 60 tasks × 2 prompts, Sonnet 5.5, per session)

| part | stock | laya-codex `main` |
|---|---|---|
| Claude lookup round trips | 8.91 s, 3.67 calls | **4.26 s, 1.82 calls** |
| ↳ first prompt | 4.18 s, 1.92 calls | 1.50 s, 0.65 calls |
| ↳ follow-up (callers / tests) | 4.70 s, 1.75 calls | **2.80 s, 1.17 calls** |
| UserPromptSubmit hook | — | 1.06 s (0.53 s × 2; the follow-up's half is a benchmark artefact, see WS1) |
| tool execution | 0.14 s | 0.28 s (`search` ≈ 331 ms per call) |
| **lookup time** (hook + round trips + tools) | **9.05 s** | **5.60 s** |

What sets each number:
- **A round trip is API latency.** It is ≈ 1.5 s to the first token plus ≈ 160 output tokens. The
  injected code adds ≤ 0.03 s. laya-codex can only remove calls, not speed them.
- **First-prompt lookups follow whether the gold file was inlined.**

  | gold file | prompts | lookups / prompt |
  |---|---|---|
  | inlined | 45 of 60 | 0.36 |
  | listed at rank 3–8 | 7 | 1.00 |
  | absent from the list | 8 | 2.00 |

  Stock makes about two lookups per prompt in all three groups, so task difficulty does not
  explain the gap.
- **Follow-up lookups are mostly one `search` for callers or tests.** The follow-up injection adds
  no new code in 60 of 60 sessions.
- **The hook is the model** (97%): two forward passes of 8 candidates × ~182 tokens, ≈ 260 ms each.
  Process spawn, IPC, BM25 and render add < 10 ms together.
  - The model sees only the first 128 tokens of a chunk; 92% of chunks are longer (median ≈ 380).
  - Throughput is ≈ 5.6k tokens/s and the matrix multiplies run at 5.3–5.5 TFLOPS, so kernel work
    tops out near 1.2×.
- **Ranking tests already run** (real hook, 238 gold files in tasks-v8 + held-out, paired against
  production):

  | variant | gold files, net vs production | 95% CI |
  |---|---|---|
  | keywords only | −14 | [−24, −4] |
  | 64-token window | +4 | [−3, +11] |
  | 64-token window + score 12 | −1 | [−8, +7] |

  A longer window fed to r1 without retraining did not help (2026-09-28: 70 → 67–68 of 115),
  because r1 was trained at 128.

**Expected if G1 and G2 pass (estimates, not measurements):**
- **Calls:** 1.82 → ≈ 1.0 per session (first prompt 0.65 → ≈ 0.35, follow-up 1.17 → ≈ 0.6).

- **If G2 fails:** ≈ 1.5 calls and ≈ 4.4 s.

## Workstreams

### WS1 Measurement fixes (first; ~1 day; no ranking risk)

Branch `fix/bench-lookup-time`.

1. **Benchmark follow-ups the way users run them.**
   - Today `bench/run_bench.py` sets `LAYA_CODEX_MEMO=0`, so the follow-up re-scores a ranking
     that is identical to prompt 1's (60/60). That costs ≈ 0.5 s per session that users don't pay
     (12 ms with the memo on, 40/40 hits).
   - Add `LAYA_CODEX_MEMO_SALT`, mixed into the memo key in `crates/laya-cli/src/daemon.rs`.
   - The harness sets a salt per (arm, task, repeat), so no run can read another's cache.
2. **Stage timers in the capture record.**
   - Add `stage_ms` (lexical, model batches, render) to `$LAYA_CODEX_HOME/capture/requests.jsonl`.
   - Port the profiler's timers from `stage-timers.patch` without the debug output.
3. **Atomic hook-log lines.** v14 has an interleaved, corrupt line from two concurrent appends.
   Write each line with one `write(2)` on an `O_APPEND` file.
4. **A lookup-time metric.** `bench/time_breakdown.py` reports hook + round trips + tools per
   session and lookup calls, with paired bootstrap CIs.
   - Note in the docs that the stream's `ttft_stream_ms` includes the hook.

- **Tests (red first):**
  - salted keys differ, and unsalted keys are unchanged;
  - a concurrent-writer test for the hook log;
  - `stage_ms` is present in the capture record;
  - `test_time_breakdown.py` covers the new metric.
- **Gate:** the replay inlines identical lists with the memo on, and follow-up hooks hit the cache
  (capture shows `scored` from cache).

### WS2 Feasibility spike: smaller model, longer window (~1 day; before any training)

Branch `spike/base-window` (not merged).

1. **Can candle load it?** Check that `crates/laya-model` loads a ModernBERT-base config
   (`answerdotai/ModernBERT-base`, 22 layers, hidden 768) with the noul decision head. Every
   dimension must come from config, with no large-only constants.
2. **Time it.** Run `crates/laya-model/examples/bench.rs` (random head weights are fine) for:
   - windows W ∈ {256, 384, 512} code tokens;
   - candidates K ∈ {12, 16, 24};
   - arms alternated to cancel the machine's memory-pressure drift.
3. **Pick (W, K)** with p50 ≤ 450 ms (leaving 50 ms for the rest of the hook). Expected: base is
   ≈ 3× faster per token than large, which gives roughly W = 512 at K ≈ 12–16 or W = 384 at K = 24.
4. **Find the candidate-pool ceiling.** Use the existing replay with a pool of 48 (cap 3 per file)
   to count how often gold enters the pool but misses the top 24. The 2026-09-28 figure was K = 48
   gated: +4 of 115.

- **Go/no-go:** no (W ≥ 256, K ≥ 12) fits under 450 ms → fall back to **r1 at 64 tokens scoring
  all 24 candidates** (config only, ≈ 0.47 s). Replay it for G1 and skip WS3.

### WS3 Train the whole-chunk student (local M4 Pro, ~2–4 days)

Branch `feat/laya-code-s512`.

1. **Data.** Rebuild the training lists from `data_v3` with chunks rendered at W code tokens
   (`finetune/build_data.py`, `finetune/candgen`).
   - Same 7 training repos and held-out repos as r1 (`finetune/runs/r1.json`).
   - The leakage check (`finetune/leakage.py`) passes.
2. **Model.** Initialise from `answerdotai/ModernBERT-base` with the laya noul head.
   - Loss: r1's listwise gold loss (`finetune/listwise.py`) plus knowledge distillation from r1's
     probabilities.
   - Ablation: with and without distillation, on the validation lists.
   - Use gradient checkpointing; the machine has 24 GB and already swaps.
3. **Calibrate, export, check parity.** Run `finetune/calibrate.py`, then export with
   `finetune/export.py` in the laya-code layout and record the run manifest
   `finetune/runs/s512.json`. Rust vs torch parity must pass the 7 checks on CPU and Metal.
4. **Gate G1** through `bench/replay_decide.sh --candidate-model-dir`, with
   `LAYA_CODEX_STATE_TOKENS=W` and `score_top=K` from WS2.

- **Main risk:** the student starts without laya's pretraining, which r1 had. Mitigations, in
  order:
  1. distillation from r1;
  2. a larger W (384/512) to give it more evidence;
  3. fall back to r1 at 64 tokens with 24 candidates (WS2's no-go path).
- **Stop rule:** if two training runs miss G1, stop, write up, and ask the owner.

### WS4 Ship the model and the wider pool (~1–2 days, after G1)

Branch `feat/whole-chunk-rerank`.

1. **Defaults.** Set `state_tokens = W`, `score_top = K`, and a lexical pool of 24 → up to 48 if
   WS2 shows recall gain, all in `crates/laya-cli/src/config.rs` and the retriever.
   - Size the best-first budget to the hook's p50 ≤ 0.5 s.
   - Keep the 1.2 s hard ceiling for the fail-open fallback.
2. **Speed up `search`.**
   - Run its file ranking alongside the file scan; it must be byte-identical on the 53 replayed
     lookups.
   - Score with the new model under its 400 ms budget, so lookups stop being `laya-partial`
     every time.
3. **Distribution.**
   - The model manifest and the installer pin go to a new HF branch, `s512`; the owner uploads
     it, and `main` and `r1` stay untouched.
   - `laya-codex doctor` reports the model and window.
   - Check the Linux CPU path: it must degrade to `laya-partial` / lexical inside the budget and
     never block.
- **Tests (red first):** config defaults, budget sizing, a parity fixture for the new model, and
  the fallback under an injected slow scorer.

### WS5 Follow-up: inject the callers and tests Claude would search for (parked 2026-10-07: G2 not reachable, see Progress)

Branch `feat/follow-up-picks`.

1. **Input.**
   - On a follow-up prompt, the hook reads Claude's last answer from the hook input's
     `transcript_path`: local only, read-only, fail-open.
   - It collects the code names the answer discusses: backticked identifiers and the definitions
     shown in prompt 1.
2. **Candidates.** For each name, gather usage sites and tests with the existing machinery (the
   exact name scan behind `search`, `test_refs`, `usage_lines`).
3. **Pick with the model.**
   - The student (or r1 until WS3 lands) scores (follow-up question + the name's context) against
     each usage/test chunk.
   - The top picks are injected as file:line lists plus at most one short block, under a char
     budget sized to stay cost-neutral.
4. **Latency.**
   - The follow-up hook must also hold p50 ≤ 0.5 s.
   - If it can't, rank in the background when Claude's first answer ends (`Stop` hook), and let the
     follow-up hook read the result.
5. **Gate G2 offline** on the v13 + v14 follow-ups, before any wiring into the default path.

- **Why this can work where 2026-09-30 failed (41% covered):**

  | old failure | what this design changes |
  |---|---|
  | names chosen by rule | names chosen by the model with the follow-up question in view |
  | names not in prompt 1 | names read from Claude's own answer, which holds 93% of the names it then looks up (2026-09-30) |

  It still cannot cover Reads (22 of the old misses) or names with more than 60 uses.
- **Stop rule:** G2 below 50%, or not cost-neutral → park the branch, write up the replay (like
  PR #36), and don't retry without new evidence.

### WS6 Decisive run and release (after WS4, and WS5 if G2 passed)

1. **Paid run.** Held-out tasks (`bench/tasks-heldout`), 3 arms (stock / `main` / candidate), pinned
   `--model claude-sonnet-5-5`, harness from WS1.
   - **Estimate ≈ $21, cap $25. Needs the owner's approval before launch.**
   - Quote cost from `bench/recost.py cold`, and record the rank mode per prompt.
2. **Report.** `docs/RESULTS.md` gets the balanced table (quality, time, lookup calls, cost, code
   read + injected); VISION gets a decision-log row and an update to its targets table.
3. **Release.** Version bump (Cargo, plugin.json, candgen lock), CHANGELOG, tag, formula. Each step
   asks first.

## Order and dependencies

```
WS1 ─┐
WS2 ─┼─► WS3 ─► WS4 ─┐
     └─► WS5 (offline G2 with r1; swap in the student after WS3) ─┴─► WS6
```

WS1 and WS2 run in parallel (WS2 owns the GPU). WS5's offline design starts with r1, so it doesn't
wait for training.

## Risks

| risk | effect | mitigation |
|---|---|---|
| The base student is weaker than r1 (no laya pretraining) | G1 fails | distillation from r1; a larger W; fall back to r1 at 64 tokens × 24 candidates |
| Memory pressure (23/24 GB, swap) skews timings and slows training | false speed claims | alternate arms side by side; time on an idle machine; gradient checkpointing |
| More injected follow-up text raises cost | cost target broken | char budget derived from G2's cost-neutral rule; G3 checks cost vs `main` |
| Claude reads more when shown different code (v11) | tokens up, calls not down | G3 measures calls and read + injected; injection size held at ±2% for the first prompt |
| Reading the transcript in a hook | privacy / brittleness | local, read-only, fail-open; nothing leaves the machine; the capture records hold no code text |
| Linux CPU is ≈ 10× slower | the hook falls back to partial ranking | budgeted best-first stays; a smaller model also helps CPU |

## Rollback

- The model ships on its own HF branch, behind the installer pin. Reverting the pin restores r1.
- The window, pool and score_top are config defaults, and each is one revert.
- The follow-up picks have their own branch and default switch.
- Hooks fail open throughout.
