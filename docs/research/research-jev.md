# Research: "Jev" (TypeSafe AI), claude-jev plugins, and implications for laya-codex

Date: 2026-09-23. Researcher: athena-researcher.

## 0. Headline finding — read this first

**The entire "claude-jev" ecosystem, and the Laya model laya-codex is built on, were all created in the same ~1-week window (2026-09-16 to 2026-09-22), immediately around TypeSafe AI's stealth-launch date (2026-09-15).** This is not proof of fraud, but it is a strong "inorganic/promotional cluster" signature that must gate every downstream decision:

- GitHub search `jev+claude` returns **274 repos**, effectively all created 2026-09-16→09-22. `claude-jev` (exact name) returns 25 repos, all in the same window. [github.com/search API, verified 2026-09-23]
- `tamaratran/fast-jev-compaction`: **6,258 stars**, 351 forks, 72 open issues — but only **2 contributors** and created 2026-09-17 (~6 days old at query time). Star count this size in under a week with 2 contributors is not an organic OSS growth curve. VERIFIED via GitHub API (counts), UNVERIFIED whether stars are bot-inflated (no direct proof, but the shape matches known star-farming patterns).
- **`convaiinnovations/laya` itself — the model laya-codex depends on — was created 2026-09-18** (5 days before this research), has **0 downloads via the HF API but 2,374 likes**. Per this agent's own prior methodology memory (`hf-model-diligence-methodology.md`): "downloads:0 + high likes, created in last 1-2 weeks" is a documented red flag for unreliable popularity signals. The Laya model card explicitly frames itself as a benchmark competitor to Jev ("Laya vs Jev" charts in the repo), i.e. Laya and Jev appear to be marketing counterparts launched in the same campaign/window, not independently converged designs.
- Multiple `claude-jev` README variants (across unrelated GitHub accounts) reuse near-identical marketing phrasing ("System One model," "typed judgments, not text," "calibrated probabilities," fail-open language) — consistent with either a shared template TypeSafe distributed to launch partners, or LLM-generated repos produced for a hackathon/bounty/SEO push tied to the Sept 15 stealth launch.

**Recommendation gate: treat every "claude-jev" repo as an unaudited, week-old, single/two-maintainer artifact. Do not install or depend on any of them. Borrow patterns only, verified independently against the official Claude Code hooks docs (see §4).**

### `session.compact` — does this hook exist in Claude Code? **NO, not under that name.**

Official docs (code.claude.com/docs/en/hooks, WebFetched 2026-09-23) list compaction-related hooks as **`PreCompact`** and **`PostCompact`** only. Quote from the docs fetch: *"There is no hook called `session.compact`... These hooks cannot replace Claude Code's compaction/summarization behavior itself. They fire before and after the compaction process occurs... they do not allow you to override or customize the actual compaction algorithm or summarization logic."*

This directly **contradicts** the claude-jev README claim that a `session.compact` "experimental function hook" lets Jev's picks *replace* the compaction summary so "the summarizer never runs." Either:
(a) the plugin authors are using an internal/undocumented/beta hook name not yet in public docs, or
(b) they're describing a client-side re-injection trick built on top of `PostCompact` (append/override context after the fact, not truly replacing the summarizer), or
(c) the claim is simply inaccurate/aspirational marketing copy.

**VERDICT: UNVERIFIED-LEANS-FALSE. Do not assume a compaction-override hook exists in Claude Code.** If laya-codex wants to keep top-ranked spans alive across compaction, the only documented mechanism is `PreCompact` (to snapshot/export what you care about before compaction runs) + `PostCompact` (to re-inject it afterward) — not a summarizer replacement.

## 2. Jev / TypeSafe AI — what it actually is

- TypeSafe AI: "San Francisco lab that came out of stealth on September 15, 2026 with $40M in seed funding" (per aggregated search-engine summaries of secondary blog posts — flaviocopes.com, dev.to, datacamp, truefoundry, langchain blog — **all themselves published within days of the same launch, i.e. secondary sources parroting the same press kit, not independent verification**). UNVERIFIED against a primary funding announcement (no TechCrunch/Crunchbase pull performed); treat funding figure as PR-sourced.
- Primary site `typesafe.ai` resolves (HTTP 200, verified via curl). Docs at `docs.typesafe.ai` (308 redirect → `/introduction`, resolves). Console at `console.typesafe.ai`. Careers page on Ashby. These are real, live endpoints — the *company* is not vaporware, but is **brand-new (≤1 week old public presence at research time)**.
- Positioning: "System One model" (Kahneman fast/intuitive-thinking framing) — takes program/agent state + typed questions, returns **typed decisions + probabilities** in one parallel pass, not token-by-token text. Trained with "Reinforcement Learning for Calibrated Decisions (RLCD)" (proprietary term, no paper found/verified).
- **API shape** (from `docs.typesafe.ai/concepts/system-one`, WebFetched): three response primitives — `noul` (probability/binary), `choice` (categorical softmax), `score` (ordinal). Access via SDKs or `POST /v1/systemone`. **This is the identical taxonomy Laya uses** (`choice`/`score`/`noul`) — confirms Laya was explicitly designed as an open-weight, self-hostable analogue/competitor to Jev, not an independent invention. VERIFIED (both model card and TypeSafe docs use the exact same three terms).
- **Architecture**: TypeSafe does not disclose Jev's base architecture, parameter count, or whether it's open-weight anywhere in the fetched docs pages. All public benchmarking (latency, accuracy) comes from the *Laya* model card's own comparison charts (`laya_vs_jev.png` etc.), i.e. a competitor's self-reported numbers — **not from TypeSafe directly**. UNVERIFIED / one-sided source.
- **Pricing**: two inconsistent figures seen across sources — search-engine summary said "$0.042 per million input tokens, free output"; direct site fetch said "$42 per billion input tokens" (same magnitude, differently phrased — consistent, not contradictory) with a claim of "238x lower input price than Claude Fable 5.1" and "193.6x Faster, 444.6x Cheaper" vs frontier LLMs on System One tasks. These are TypeSafe's own marketing superlatives — UNVERIFIED by any third-party benchmark.
- Laya's own model card (self-reported, so also not neutral) claims Laya is **6–8x faster than Jev** (32.8ms vs 236–276ms) but **loses badly on high-cardinality label spaces** (>20 options): Jev 0.870 vs Laya 0.425 accuracy on Banking77. This is the single most concrete, falsifiable technical comparison found — but it is self-reported by the Laya side, so still needs independent replication before laya-codex leans on it. Confirmed architecture: `ModernBertForMaskedLM`, hidden_size 1024 (ModernBERT-large-class), VERIFIED by reading raw `encoder/config.json` directly from the HF repo (not just the card prose), per this agent's standing methodology.
- Is Jev open weights? **UNVERIFIED / evidence points to hosted-API-only.** No GitHub repo, no HF repo, no self-hosting instructions found anywhere in the docs pages fetched. All claude-jev plugins integrate via an API key (`console.typesafe.ai`), never via local weights.

## 4. What laya-codex should adopt vs. skip

| Pattern | Adopt / Skip | Why |
|---|---|---|
| Typed question schema: `choice` / `score` / `noul` as the three response primitives | **Adopt** | Laya's own model natively emits these three heads — this isn't borrowed from Jev, it's literally what the model produces. Design the Rust request/response types around exactly these three variants (tagged enum), matching what both Laya and Jev converged on. |
| Fail-open on every hook (error/missing key/timeout → emit nothing, never block) | **Adopt** | Sound reliability pattern regardless of provenance — matches the global CLAUDE.md rule "design for failure: timeouts, retries, circuit breakers." For laya-codex (local Rust binary, no API key/network dependency since Laya is self-hosted) the failure modes are narrower (model load failure, tree-sitter parse failure, timeout) but the fail-open principle still applies: on any ranking failure, hooks should pass through with no injected spans rather than blocking the turn. |
| Local skip rules (slash commands, `#`-prefixed lines, prompts <3 chars skipped before calling the model) | **Adopt** | Cheap, sane pre-filter that avoids wasted inference on trivially-uninformative prompts. Directly portable to a `UserPromptSubmit` hook if laya-codex adds prompt-routing later. |
| `PreToolUse` (Agent\|Task) hook to pass ranked spans into subagent context | **Adopt, but redesign the trigger** | The *goal* (give subagents the top-ranked chunks, not just the parent's context) is directly relevant to laya-codex's mission. Don't copy Jev's tier-selection use case — instead use `PreToolUse` on `Task`/`Agent` tool calls to inject the top-10 Laya-ranked spans relevant to the subagent's stated objective. |
| `session.compact` as a way to "replace the compaction summary" | **Skip as described** | Confirmed against official docs: no such hook exists; `PreCompact`/`PostCompact` cannot override the summarizer. If laya-codex wants ranked spans to survive compaction, implement it as: `PreCompact` hook exports Laya's current top-N ranked spans to a side file; `PostCompact` hook re-injects them into context. This is a documented, real mechanism — do not promise "summarizer never runs." |
| `PostToolUse` (edits) "judge the edit against instruction files" using 40-question cap, deterministic lookups | **Adopt the shape, not the content** | The "cap total judged questions per hook call, use deterministic/cheap checks before model calls" pattern is a legitimate cost-control idea worth reusing for any Laya-driven `PostToolUse` hook laya-codex builds (e.g., re-rank affected chunks after an edit) — cap the number of chunks re-scored per edit rather than rescoring the whole tree. |
| Calling Jev instead of / alongside Laya | **Skip — do not add a dependency on Jev** | (1) Jev is hosted-only, requires an API key and network round-trip (236–276ms per Laya's own benchmark) vs Laya's local ~33ms — directly against laya-codex's presumed goal of a fast local Rust tool with no network dependency. (2) TypeSafe AI and the entire Jev ecosystem are ≤1 week old at time of research with unverified funding claims, no independent benchmarks, and a GitHub ecosystem showing signs of inorganic growth (bot-scale stars on a 2-contributor, days-old repo). (3) Jev's only real edge — better accuracy at >20-option label spaces — is not laya-codex's use case (ranking/scoring tree-sitter chunks is a scoring/ranking problem, not a high-cardinality classification problem). If a genuine need for a hosted high-cardinality judgment model ever arises, revisit Jev only after it has a longer independent track record. |
| Architecture pattern (`src/{adapters,application,domain,infrastructure}`, hexagonal) seen in buchmark/claude-jev | **Adopt if it fits laya-codex's existing Rust module layout** | Generic clean-architecture separation (model I/O adapter vs. hook-handling application logic vs. domain types for choice/score/noul) is sound engineering independent of the plugin's other problems — worth mirroring in the Rust crate layout (e.g. `src/adapters/laya_model.rs`, `src/domain/judgment.rs`, `src/application/hooks/*.rs`). |
| Trusting any specific benchmark number from TypeSafe or Laya marketing (latency, cost multipliers, "never hallucinates") | **Skip / re-verify independently** | All performance numbers found are self-reported by one side of a two-company launch cluster. Before laya-codex's docs cite any Laya-vs-Jev number, re-run the benchmark independently rather than repeating the model card's chart. |
